# Independent measurement review

The common opening workload can support a narrow speed claim when validation work is equivalent. It does not support a whole-game or search speed claim. Each engine starts at a valid two-player opening with bank [4,4,4,4,4,5], empty player token holdings and no bonuses. Clone the complete native state, take white, blue and green, advance to the second player, consume the output, then destroy or release the clone. Do not generate all legal actions inside this timed region. The ranked checked workload must use native action validation on every iteration. Validate complete input/output equality within each engine; unchanged random markets cannot affect this action.

Native state sizes and API costs differ. The Rust clone copies its native state. The C++ clone includes heap allocation when its native API requires this. The Numba Board copies its array and rebuilds views using its unmodified copy_state API. These costs belong to clone plus apply. This comparison cannot isolate arithmetic application cost, and it is not a proof of full rule equivalence. State representations need not have equal byte size to perform the same operation.

The Python compiled adapter uses an njit loop and calls unchanged upstream Board methods. Board.make_move has no direct validator; valid_moves enumerates its entire distinct action set. Thus, its adapter validates the fixture before the timer and records rank_eligible=false. It is an unchecked API reference and cannot share a rank with the checked Rust and C++ operations. Adding an adapter-only fast validator would conceal a semantic difference and is not permitted here. Its checksum reads output bank, player tokens and next player on every iteration. The public-api mode includes Python dispatch through SplendorGame.getNextState and must be reported as a separate interface measurement. Report Numba compilation separately. Do not compare a cold JIT process to an already warm release binary. The four-thread compiled adapter releases the GIL in the batch function and gives each worker a separate mutable Board; workers share only the immutable input array. The timed region includes dispatch and reduction, but excludes thread-pool setup and teardown.

Whole-game random results cannot share a rank when legal action distributions differ. Splendorust separates payment, return and noble phases. Engines that collapse these phases must report completed player turns as well as engine transitions. Uniform choice of a main action plus uniform payment is different from uniform choice of all combined action payloads. A deterministic fixed policy also needs the same feature inputs, stable tie order and hidden-information restrictions. Reusing a numerical seed with different PRNGs is a reproducible schedule, not a paired trajectory.

Count normal completions, no-action stops, illegal moves and caps separately. Completed games per second uses only normal completions in its numerator. All attempted trajectory work remains in elapsed time. A cap is an incomplete trajectory, even if upstream code awards a winner at that cap. Latency percentiles over attempted trajectories and over completed games answer different questions; label both. Per-game timers include policy choice if the measurement is a game runner; they do not measure pure engine arithmetic.

Search results need separate records for root selection, rollout rules, state determinization, simulations, search depth, thread count, inference model and hardware. Two implementations with 128 simulations can do very different work. Record simulated transitions and wall-clock cost, and never treat equal simulation counts as equal compute. Search on full deck information is not comparable to search that gets only an observation.

Use at least seven serial repetitions after smoke validation. Alternate engine order across repetitions. Run no builds, candidate setup or other benchmark workload concurrently. Show each raw duration, median, range and a repetition-level interval. A bootstrap interval over a few timed repeats describes measured run variability; it is not a portable machine guarantee. Avoid a fixed tiny iteration batch: timer resolution and process scheduling can dominate. Use enough iterations for the measured region to last at least one second. Do not pool millions of correlated iterations as independent samples.

Remaining risks are shared-machine scheduling, thermal drift, unequal public API work, different native state representations, and an opening-only fixture. Add a corpus of identical reachable midgame states and mapped payment/return/noble decisions before claiming general transition throughput. Add full-game parity traces before ranking completed game rates. Preserve known non-comparable engines in the candidate register.
